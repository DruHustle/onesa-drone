# Drone managed human identity

The Drone API can receive managed RS256 access and ID tokens through the registered HTTPS callback with PKCE. Configure the existing client credentials, `ONESA_IDENTITY_ISSUER=https://auth.onesa.eu/`, a dedicated `ONESA_IDENTITY_AUDIENCE`, `ONESA_IDENTITY_JWKS` containing trusted current and next public signing keys, `ONESA_IDENTITY_MAPPING_ISSUER` equal to the historically commissioned Portal issuer, and `ONESA_IDENTITY_ACCOUNT_URL` for account self-service. Refresh keys before rotation and immediately distribute emergency key removal. The native app uses the system browser and its existing independent one-use device proof. The original issuer namespace and stable user UUID keep the native encrypted account storage scope unchanged.

Run the established Drone schema initialization on the restored staging database, then import the independently verified Identity export with `python -m backend.app.managed_memberships /private/path/to/snapshot.json` and the Drone database URL. A dry rehearsal on the restored database must reconcile the approved tenant IDs, scoped roles and counts before cutover. Reimporting an identical snapshot preserves memberships. An unknown tenant, duplicate, or changed product-owned role interrupts the transaction. Reconcile post-cutover grants, removals and role edits before switching authorities. The importer adds missing grants and keeps existing local rows; it does not process deletions from a stale snapshot. Product audience and role cap tenant membership. An ordinary account without a local Drone tenant grant sees zero workspaces. Account access is separate from hardware, telemetry and recovery. Only synthetic read-access workflows have been qualified in this candidate.
